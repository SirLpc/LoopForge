# Runner 预热工作区池

## 目标

Unity 项目的 Git 检出和 `Library` 可达几十 GB。运维在执行机器上预先准备多个完整项目目录。LoopForge 根据项目设置，把目录独占分配给需要访问项目仓库的 SOP 或对话，复用本地 Git 对象、已检出的资产和 Unity 导入结果。池内目录全部被占用时，任务和对话排队等目录。

预热工作区采用 Git 交付和原目录保留两种方式保存工作。只有能从 Git 和已归档产物恢复的目录才能归还。预热工作区的生命周期禁止创建、上传或恢复整目录快照，包括对话轮次结束、切换、空闲回收、取消和自动清理。

## 方案比较

- **直接租用完整目录，已选定。** 直接复用运维准备的 Git 检出和独立 `Library`，每个目录对应一份并发容量。需要独占租约，以及能保护未交付数据的归还流程。
- **写时复制预热模板。** 每个工作区创建可写副本，保留旧工作区和清理模板更容易。需要支持写时复制的文件系统，副本也会随写入累积磁盘占用。

## 项目配置与目录登记

项目设置提供「普通检出」和「预热工作区池」。新项目和没有该字段的项目按普通检出运行。使用现有的项目管理权限和表单。创建工作区时冻结模式、项目、仓库、目标分支和现有执行目标。切换项目设置后，新建的工作区使用新设置。继续或显式借用已有工作区时按其冻结配置操作。

运维在 Runner 本机配置文件中登记每个目录。每条记录包含稳定的槽位 ID、项目 ID、仓库 ID、绝对路径和相对于仓库的 Unity 项目路径。目录是专用于 LoopForge 的普通 Git 检出，`origin` 匹配平台登记的仓库，Unity 项目路径允许仓库根目录。Runner 保留该 Unity 项目下 Git 已忽略且无跟踪文件的 `Library`。运维可声明该 Unity 项目下的 `Temp`、`Logs`、`obj` 为可清除的生成目录，Runner 清除前同样检查忽略规则、跟踪文件与路径类型。其他被忽略文件按用户文件处理。目录与运行根目录位于同一文件系统，使用原子改名移入和移出运行目录。运维只在空闲且已排除调度的目录上手工运行 Unity 或维护检出。

Runner 向平台登记能力、项目与仓库对应的槽位 ID 和状态。路径和维护配置留在机器本地。登记时验证 Git 远端、目录和缓存位置，拒绝符号链接、重复路径、父子重叠及与 Runner 运行路径或状态目录重叠的配置。Runner 升级、离线、未登记目标仓库与目录暂时占满使用不同状态提示。

目录复用限于经运维授权、互相信任的同一项目和仓库执行环境。`Library` 可以包含编译结果，因此它随槽位留在该信任范围内。每次打开仓库都按现有项目权限检查，并用当前操作人的 Git 凭据访问冻结远端确认仓库授权。共享对话中换发言人时同样校验，已有租约只维持目录归属。Runner 管理的可复用 Git 对象只通过可信远端或已验证的运维种子写入。工作区使用租约独立的可写 Git 元数据，读取受控的本机 Git 对象缓存。前一租约的 Git 配置、hook、reflog、本地对象、凭据和沙箱 HOME 均只属于前一工作区。Git 对象缓存通过现有沙箱隔离机制只读接入。

## 工作区入口与排队

- **SOP。** 从已有的冻结仓库上下文确定需要的仓库和工作分支。执行同一工作区的节点、重试和共享工作区的子 SOP 使用同一租约。一个运行需要多个仓库时一次性分配一组槽位，分配失败前不占用部分容量。没有仓库需求的运行直接使用普通工作区。
- **普通对话。** 对话需要访问仓库时，Main Bot 在现有 `workbench_workspace_open` 请求里提供项目登记的 `repositoryId`，用户未指定仓库时可使用项目默认仓库。平台校验仓库属于本项目。项目文本对话和仅用于产物的空工作区无需入池。接着操作已有工作区时优先复用现有绑定。有明确的新仓库请求时，按运行环境和仓库两者定位可复用工作区。任务对话、借用 SOP 和 IDE 通过原有工作区归属进入。
- **排队。** 等待的单位是工作区所有者。任务和对话针对同一 Runner 进入同一持久队列，按照入队顺序分配能满足全部仓库需求的最早请求。已获得该工作区的后续操作可以继续，以便结束时释放。等待状态沿用运行事件和对话进度，显示「等待预热工作区」并支持停止或取消。等待不占 Runner 命令并发名额，Git 和 CLI 的执行超时从各自实际开始时计算。等待由可恢复的队列驱动，控制请求及时返回排队状态，控制面重启后继续同一请求。已选机器临时离线时保留已入队请求，有效目录不足时继续等待。若有仓库从未登记、配置无效或执行目标不支持，明确提示需完成登记或更换执行机器。预热工作区申请只可由池分配器完成。

项目权限沿用现有入口。SOP 知道所需仓库后，云端选择器只考虑支持该模式且登记了完整仓库组合的 Runner。新云端对话在第一轮就绑定执行机器，因此优先选已登记项目默认仓库的兼容 Runner。项目文本对话可用常规云端执行目标。后续打开指定仓库时只检查会话已选机器，缺少登记时告知在原机器登记该仓库或选择已登记的机器新开对话。兼容性与暂时没有空位分别判断。已存在的租约和未交付改动按原机器恢复。Docker 和 native 沙箱需要通过进程回收、路径隔离和只读 Git 缓存验证，才可在 Runner 上为预热请求声明支持。

对话切换已有工作区时，先结束使用旧目录的 CLI 阶段，再等待新目录。旧目录通过安全检查后可立刻归还并参与分配，绑定在新目录准备好后切换。若唯一可用的容量属于该会话且原目录仍有未交付内容或终端，保留原绑定并提示先处理阻碍。用户停止等待时，原绑定仍可用，已经归还的原目录可按记录重新领取。

## 领取和同步

控制面保存排队与归属，Runner 本机验证并独占处理真实文件系统。队列条目以工作区所有者去重。Runner 在已注册目录或已知运行位置之外保存持久的槽位状态和操作记录，状态至少能区分空闲、准备、已分配、归还及待人工检查。目录迁入现有 `runs/<owner>/workspace/<repo-dir>` 布局，沿用文件浏览、IDE、终端、浏览器、产物、交付和原生 CLI 的工作区入口。槽位状态记录工作区所有者与分配代次，准备和归还持有工作区独占门闩，迟到请求必须验证归属及代次后才能操作。

首次领取用当前操作人的已有 Git 凭据从冻结远端获取目标引用，再对已有文件执行增量 checkout。按 SOP 已有分支语义新建或继续工作分支，对话默认从所选仓库的默认分支开始。Git LFS 按仓库原有设置取得缺少的资产。准备保留已存在的 `Library` 和未变化的源文件，避免重新克隆、复制工作树或重写未改变的文件。后续操作沿用现有检出和工作分支。远端验证、同步、分支校验或沙箱初始化失败时保留原文件并反馈可操作错误。确认状态安全后退回空闲，否则标记待人工检查。

Runner 重启时核对操作记录、目录位置、工作区所有者和残留进程。归属不明或目录缺失时保留绑定并标记待检查。Runner 或控制连接的租约过期只使会话重连，只有确认旧进程退出并完成归还后才能再分配。重复申请、重复取消和重复归还按相同分配代次幂等处理。

## 归还与恢复

1. SOP 结束、对话切换或空闲回收时检查归还条件。有排队请求时，优先检查已经结束本轮的对话工作区，无需等满默认空闲时间。仍在运行或等待审批的 SOP、打开的终端、IDE 写操作和活跃的对话进程继续占用槽位。取消会停止当前执行并保留工作区归属，随后按同一条件判断能否归还。
2. 在原工作区停止并确认退出所有相关进程，归档 SOP 已声明的产物，再检查每份检出。索引、工作树和子模块必须干净，进行中的 Git 操作、stash 和未被标准交付涵盖的本地引用都需原所有者处理。当前工作分支或 detached HEAD 记录精确提交，并验证该提交可由冻结远端取得。新建但尚未推送的当前工作分支，只有提交可从远端取得且分支名能从记录重建时才可归还。其他本地分支、标签及命名引用需要在冻结远端有同名同提交的引用，即使提交本身已在远端可达也是如此。检查使用当前操作人的 Git 凭据。自动回收时，SOP 使用运行责任人，普通对话使用最近访问仓库的授权操作人。凭据不可用时保留原目录并提示通过已有权限重新打开工作区处理。

   工作区内的用户文件必须已由 Git 或现有产物系统按原路径、原内容保存且可恢复。已归档的 SOP 产物只有通过此条件才算可交付。对话回复中的脱敏文本附件只用于展示，无法复原的二进制文件和其他未交付文件会保留在原目录。安全检查跳过 Runner 拥有的运行时文件和在登记时明确允许处理的 Unity 生成目录。目录留用时，状态说明需要提交并推送、归档或处理哪些内容，原任务或对话仍可打开。删除请求也先检查这些条件，存在待处理数据时保留入口并返回可操作冲突。
3. 安全归还先记录工作分支和精确提交以及产物关联，随后回收本轮运行时文件，将检出与 `Library` 原子移回预热区，确认持久状态后将槽位标记为空闲。普通目录删除和快照导出路径需要检查预热模式与活跃槽位标记，文件系统操作失败时保留归属并允许恢复。这种设计的取舍是未提交、未推送或尚未归档的工作会继续占用槽位，直到原所有者处理完毕。
4. 已归还的任务或对话再次需要项目文件时重新排队。领取后从记录的分支与提交重建工作状态并恢复既有产物。只有首次开启工作区按目标分支最新提交初始化。恢复时若无法取得原提交，显示相关分支和提交信息供处理，保留历史记录。当原机器或其磁盘不可用时，本地未交付内容只能从该机器的原目录找回。

## 实现边界与验收

项目配置归 `ProjectsRepo` 和 `projectsHandlers`，Runner 登记与目录等待队列归 `RunnersRepo`，运行生命周期和归还后的引用记录归 `RunsRepo`。引擎编排现有 SOP 与对话入口，Runner 负责本机目录验证、Git 同步、进程围栏和原子迁移。沿用仓库的增量 DDL 和手动迁移约定。前端沿用项目表单、运行状态和对话进度组件。配置文件示例使用虚构路径和 ID。

为便于 fork 同步上游，预热池专属逻辑集中在现有领域包内的独立文件。尽量复用既有配置、协议和生命周期接入点。现有文件中的改动限于字段与装配、模式分派，以及防止原清理或快照流程进入预热目录所需的检查。评审时核对每处上游文件的改动是否可收敛为接入点。

- 两个真实预热目录对应两个并发工作区。第三个 SOP 或对话显示等待，停止等待不会留下槽位绑定。归还后队列中的下一个可满足请求继续。
- Git 远端前进后，新工作区拿到最新目标提交和原目录的 `Library`。原工作区用同一分支继续，回收后的干净会话可从记录的提交恢复。验证新建分支、继续已有分支、只读分支和 Git LFS。
- 用小型测试仓库验证快照创建入口均未被调用，目录移动复用 inode，不复制整目录。覆盖未暂存和已暂存改动、本地提交、未归档文件、失败的远端验证、凭据和 Git 元数据隔离、取消与重启、迟到的释放请求，以及同一 SOP 的节点和对话借用同一目录。
- 覆盖单槽位同仓库切换、被占用时排队、目录配置错误、旧 Runner、离线、权限失效、仅本地分支或标签，以及归还时仍有活跃进程。现有普通检出测试和对话快照恢复测试继续通过。真实 Unity 验收用同一仓库记录首次进入、目录复用后进入和 Unity 测试启动时长，核对 `Library` 在归还后可再次使用。
