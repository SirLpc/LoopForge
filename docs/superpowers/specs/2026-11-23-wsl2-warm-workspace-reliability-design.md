# WSL2 原生预热工作区借还可靠性

## 目标

WSL2 原生 Runner 继续通过私有 bind mount 借用 Windows 项目的原始 Git 检出。每个目录有一个独占租约，Windows Unity 验收使用原路径和同一份 `Library`。借还过程中需要保护本地源码、索引、分支和忽略文件，并在网络中断、Runner 重启或 Windows 侧写入后正确恢复归属。

在 D 盘临时仓库复现了四个缺陷。Git 检出失败后租约卡在准备中。归还校验和确认之间的原目录变更可能漏检。同名分支已前进时无法恢复远端仍可取得的旧提交。新的租约可能继承旧租约的差异基线。

## 方案选择

| 方案 | 取舍 |
| --- | --- |
| A. 修复现有借还状态转换 | 用户选定。复用原生工作区、所有权和代次校验。Runner 负责恢复本地状态，平台对已失效的归还回执做一次有条件的事务更新。 |
| B. 先增加阶段诊断和计时 | 改动范围较小，能帮助定位现场卡点。四个已复现的行为仍需后续修复。 |

改动按预热功能集中放在 `internal/runner/warm_native_*`、`internal/runner/warm_workspace_*`、`internal/engine/warm_workspace_*`、`internal/repo/warm_workspace_*` 和 `internal/domain/warm_workspace.go`。公共 Git、沙箱、Runner 传输和普通工作区入口继续由现有接口承接。共享预热入口只接入原生分支和已有校验器。公共工作区请求和响应各加一个仅用于原生归还的可选回执标识。数据库变化集中在预热归还表的可空 JSON 字段，由已有 AutoMigrate 补齐。性能调优和 Studio 展示留给后续工作。

## 借用和中断恢复

Runner 在原生槽位开始修改分支、索引或工作树前，写入与租约代次关联的检出意图。日志记录槽位、起始 `HEAD` 及附着分支、目标提交及分支、目标分支写入前的引用、基线提交。一个多仓库租约逐个提交准备结果，保留已经完成的仓库和当前一个写入意图。远端授权和对象验证先于切换分支，Git 元数据与 `Library` 仍留在原检出。

重试或归还先核对槽位身份、编辑器锁、Git 状态和实际文件内容。确认工作区完整地处于写入前状态时，可以按已记录的目标和基线重试，或按未准入归还。确认工作区已完整切到记录的目标后，核对索引、文件和 LFS 指针或对象。可续做经验证的 LFS 文件写入、基线和 Git 身份记录，然后登记准备结果。归还可以按未准入规则验证已准备的仓库。脏文件、异常分支引用或不完整检出导致的歧义继续由当前租约持有，错误信息指出需检查的阶段。旧日志只有 `preparingGit` 而无检出意图时，沿用人工检查路径。

仅能证明可恢复的中断和暂时的 Unity 占用保留原预约并可重试。返回已有的忙碌或暂不可用状态，由现有等待流程再次推进。权限失败、配置不符和工作树内容存疑沿用预热工作区的留存或检查路径。Runner 保存预热阶段和可操作原因。平台错误保持相对路径，并通过现有日志脱敏处理。

## 历史提交与差异基线

重开时恢复平台记录的精确提交和工作分支。只在本地分支头位于冻结仓库最新核验的同名远端分支历史、且它是待恢复提交的后继时，允许 Runner 将这个本地分支切回旧提交。实际更新引用时比对检测到的原分支头，并保留旧分支头的本地 reflog 记录。临时处于目标提交的 detached HEAD 也属于可续做状态，前提是分支引用与日志吻合且文件校验通过。此选择保持现有的同名分支提交与交付路径，借用期间 Windows 看到的是历史工作分支。仅存在于本地的提交和分叉继续由原分支保留，Runner 给出具体阻塞原因。其他分支和标签按现有保护规则处理。远端分支遵守原有的快进式交付约束。

基线按租约激活确定。同一租约使用日志中的固定基线。新借用普通分支时以本次核验的检出为基线。有独立工作分支时使用本次取到的冻结基准分支，目标提交提供兜底。精确恢复以恢复的提交作为本次激活起点。基线对象进入原检出的对象库。Runner 在开放任务访问前，以原子替换方式写入现有 `.git/agentflow-baseline` 文件，继续使用公共的产物差异读取入口。同一租约重试沿用同一 SHA，已就绪租约使用它已有的基线，下一次激活时更新。

## 归还和回执恢复

1. `warm_release_check` 在现有租约和工作区锁下检查编辑器及执行占用、远端授权、分支、提交、索引、文件和可恢复产物。每次原生证明都有持久化的回执标识，引用数组沿用现有结构。未准入的租约可使用空引用数组，已准备的仓库仍在 Runner 日志中保存其需复核的引用。平台在现有预热归还表保存待确认的原生回执。同一行保存最近已确认的恢复引用。
2. `warm_release_commit` 收到平台持久化的回执后比对租约和回执标识。在同一组工作区锁内重新检查原目录文件、当时的分支及索引、归档清理清单和 Unity 占用。复用可信的已验证 Git 对象及 LFS 缓存做本地复核，避免再次取远端。复核成功才清理已归档文件和卸载槽位。归档删除重试允许已授权且已清理的路径缺失，变化了的文件必须保留。Runner 重启遇到未完成的原生归还时保留租约，由下一次确认重新核验。已卸载的槽位通过登记的原路径核验，只有整组成功后才公布归还。平台在确认归还的同一事务内更新已确认引用。未进入过就绪的租约归还时沿用上一笔已确认的恢复引用。
3. 若复核确定证据已失效，Runner 确认原槽位归属并恢复所需挂载，记录失效的回执标识，返回明确的错误。平台根据当前工作区使用租约、预热租约代次、状态及回执标识，在一个事务中撤销匹配的待确认回执。已就绪的工作区恢复为原所有者可用，其他租约保留归还流程。已确认的恢复引用保留，后续归还可以生成新证明。请求超时或回包丢失后，Runner 仍能识别该回执并返回相同结论。迟到的旧回执对新证明无效。暂时占用和 I/O 错误保留回执供同一操作重试。
4. 现有日志和没有回执标识的证明继续可读。旧的原生证明同样经过本地复核，失效时按原租约及旧确认提交中的内容匹配处理。历史空证明保留其中已有的确认引用。原生 Runner、API 和 Worker 需要协调升级。新版 Runner 按回执做确认，来自尚未升级平台的确认请求会保留租约供升级后重试。新版 Runner 写入新日志字段后，回退使用旧 Runner 时应先由新版处理完存量租约，再按独立 Runner 状态流程切换。

WSL 无法强制控制所有 Windows 进程。最终复核缩小校验和卸载的时间差。Windows 侧打开 Unity 或执行会修改检出的 Git 操作前，仍按现有维护入口暂停调度并等槽位归还。

## 验收

- 用 D 盘临时 Git 检出、WSL 私有挂载命名空间和本地远端复现四个缺陷。覆盖原生 Runner 重启、断在检出前和切换后、LFS 恢复、归还校验后源文件变化、旧回执重放、归还确认回包丢失、以及多仓库归还途中断开。
- 验证同名分支远端前进后能恢复精确提交。验证本地独有提交、分叉、忽略文件和 `Library` 保留。验证新借用的差异基线归属本轮，且相同租约的基线在重试时稳定。
- 验证已就绪和未准入的历史日志兼容。验证未准入但已修改的租约使用新回执并复核已准备的仓库。验证原生脏工作树和不可判定状态继续保留归属，平台事务仅处理匹配的回执，且失效及未准入归还均保留上一笔已确认引用。运行现有预热池、Runner、平台控制和 Git 交付相关测试。
