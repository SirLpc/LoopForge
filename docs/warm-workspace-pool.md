# Runner 预热工作区池

当多个工作区需要同一 Unity 仓库时，每个并发工作区可以独占一份运维预先检出的目录，直接使用其中的资产和 Unity `Library`。工作区和预热区之间以同卷改名转移目录。每份检出有自己的 `Library`，仅在同一项目、同一仓库的可信执行环境内复用。

## 项目与机器

同步升级 API、Worker、Studio 和需要使用预热池的 Runner。Runner 0.12.0 支持预热协议，配置本地池、Docker 可用且宿主进程可见性检查通过后才公布槽位。登录 Studio，在「项目管理 → 项目 → 基本信息」选择「工作区模式 → 预热工作区池」并保存。新建和历史项目默认为「普通检出」。设置只在新工作区创建时冻结。原工作区继续采用自己的模式。回退时先切换项目设置，再处理现存租约和未交付内容，然后撤下槽位。

运维在 Runner 本机保存 JSON 配置。下面是同一虚构项目、同一仓库的两份独立检出。项目和仓库 ID 必须与平台登记值一致。

```json
{
  "slots": [
    {
      "id": "example-unity-a",
      "projectId": "example-game",
      "repositoryId": "example-client",
      "path": "/srv/example/slots/client-a",
      "unityProjectPath": "Game",
      "discardGenerated": ["Temp", "Logs", "obj"]
    },
    {
      "id": "example-unity-b",
      "projectId": "example-game",
      "repositoryId": "example-client",
      "path": "/srv/example/slots/client-b",
      "unityProjectPath": "Game"
    }
  ]
}
```

运行时在现有 Runner 启动参数中加上 `-warm-workspace-pool-file /etc/example/runner-pool.json`，或设置 `AGENTFLOW_RUNNER_WORKSPACE_POOL_FILE=/etc/example/runner-pool.json`。路径、维护策略和持久日志留在机器上。每个物理目录只登记给一个 Runner 实例。槽位和 Runner 的运行根目录（例如 `/srv/example/work`）位于同一个本地文件系统。路径必须是规范的绝对路径，目录及父目录均为真实目录。槽位之间以及与运行根、状态目录和配置文件之间应彼此独立。妥善保留 Runner 状态文件、相邻的分配日志和私有缓存，同时为 Git 对象与 LFS 缓存预留磁盘。

## 准备检出与沙箱

1. 为每个槽位准备独立、完整且干净的普通 Git 检出，使用单独的 `.git` 目录和本地对象库。设置唯一的、无凭据的 `origin`，与平台冻结的克隆 URL 匹配。HEAD 必须可从远端取得，索引与工作树一致，本地分支和标签可从远端核验。先处理暂存、stash、私有引用、合并或变基现场与未跟踪文件。子模块目录应留空或尚未初始化。已填充的子模块需要人工处理。继续已有工作分支时确认该分支已经推到远端，新建工作分支时按 SOP 的分支策略准备。
2. 在与生产一致的 Unity 版本和环境中打开并关闭项目，预先生成 `Library`。`unityProjectPath` 是相对于仓库的项目目录，根目录用 `.`。仓库必须忽略该位置的 `Library`，其中不得有跟踪文件。可选的 `discardGenerated` 只接受此项目下的 `Temp`、`Logs`、`obj`。这些目录只有在未跟踪且被忽略时才能清理。第一次领取前移走预热留下的其他额外文件。手工维护前先排除调度，确认槽位空闲。
3. Runner 主机安装 Git。含 LFS 指针的仓库还需要支持 `git lfs ls-files --json` 的 Git LFS、可用的远端 LFS 服务和操作人的读取凭据。私有 HTTPS 仓库按 HTTPS 主机与端口配置凭据，并确保 Runner 能验证服务端 TLS 证书。SSH 使用已配置的主机密钥与凭据。仓库 `.lfsconfig` 指定的服务地址须与冻结的 HTTP(S) 远端同协议、同主机、同有效端口。Runner 会拒绝自定义传输覆盖。用真实的部署协议校验 LFS 下载。
4. 使用该执行机器本地 Docker 和通过隔离检查的沙箱。配置池的 Runner 启动时通过 Docker CLI 解析当前有效端点，仅接受本机 Unix socket，并为该进程内所有任务固定该端点。切换 Docker context 后需重启 Runner 才会改用新端点。SSH、TCP 和无法解析的端点会停用预热分配、执行和归还，已有租约仍可查询，恢复本地端点并重启后可继续处理。普通任务仍能使用启动时选定的 Docker。使用 rootless 或 Docker Desktop 时，需在目标机器验证守护进程和 Runner 在相同绝对路径看到相同的工作区与只读对象目录。Unix socket 需要连接到同一执行机器的 Docker。容器独占可写工作区，以只读方式读取 Runner 管理的 Git 对象。不允许特权容器、宿主 Docker socket、额外宿主挂载及突破隔离的命名空间或设备。当前 native 和 local 驱动不能申请预热目录。Runner 在启动和运行时重新扫描（通常每五分钟）检查宿主进程可见性，单次探测限时 15 秒。检查失败时停止公布容量，原有租约仍可通过控制连接处理并在归还时重新验证。Linux Runner 必须能在宿主初始 PID 命名空间读取完整的 procfs（包括其他用户的线程、文件描述符和映射），隐藏进程的 `hidepid` 或容器内不完整的 `/proc` 会阻止安全归还。macOS 归还需要能完整读取宿主进程的 root、`ps` 和 `lsof`，并须在目标机器核验本地 Docker 挂载与进程可见性。

第一次领取时，Runner 用当前操作人的凭据访问冻结远端，为**每个槽位**建立受保护的 Git 对象缓存。它核验种子与远端引用、重新打包可达对象，运行完整性检查，再建立租约独立的可写 Git 元数据。已有的源文件会增量检出。每次领取和归还仍需远端授权。LFS 缓存按项目、仓库和远端隔离。首次授权下载可能包含目标提交的全部 LFS 大对象。后续检查通过对象大小和 SHA-256 复用已验证的保护缓存，仍可能产生验证 I/O 和缺失对象下载。各阶段的实际用时取决于仓库、磁盘与网络。

## 排队、归还与恢复

- 在「执行机器 → 我的机器 → 预热工作区」查看槽位、仓库、占用状态、最近心跳和等待请求。只有绑定这台机器的用户可以打开面板。槽位的占用结合 Runner 心跳和平台租约显示，机器离线时保留已知的租约状态。等待请求按入队时间展示，调度仍优先考虑最早且所需仓库都可用的请求。
- 槽位可逐个暂停和恢复调度。暂停后，该槽位停止接受新分配，已有租约继续按原流程使用和归还。暂停设置随机器绑定保存，Runner 心跳会继续上报登记。维护目录前，先暂停调度，再确认机器在线、槽位空闲。实体槽位由 Runner 本地登记。
- SOP 和打开项目仓库的对话共享所选机器上的持久队列。两个槽位都在使用时，第三个工作区显示「等待预热工作区」。SOP 可以「取消排队」，聊天可「停止生成」。等待不占 Runner 命令并发。多个仓库一次性分配，队列优先满足最早且所需仓库都可用的请求。已排队的机器离线时保留请求。旧 Runner 或缺少登记时，按提示升级或登记仓库，也可以在兼容机器新开会话。分配时同时核对槽位的远端与请求冻结的仓库地址。修改项目仓库地址后，存量请求仍需匹配原地址的有效登记。
- 纯文本对话与空产物工作区无需槽位。对话通过 `workbench_workspace_open` 指定项目的 `repositoryId` 或使用默认仓库。再次进入同一绑定时，工作树和未交付改动留在原处。换仓库前先结束旧 CLI 阶段。若旧目录仍有未交付内容、终端或占用它的进程，可以回到原任务或会话处理。
- SOP 结束、对话切换、空闲回收或取消后，Runner 确认相关进程已退出，并核验精确提交、分支、工作树、索引、其他引用与产物。先提交并推送应保留的源码。其他文件需要由产物系统按原路径和原内容保存。展示用附件不能恢复源文件时，仍需单独交付。索引修改、未推送提交、无远端对应的引用、未归档文件、权限失效和未关闭的终端都会保留目录和原所有者。归属或物理状态存疑的槽位保持待检查。
- 归还成功后，下一位申请者可领取原目录及其 `Library`。全新工作区从目标分支当前提交开始。已归还的工作区重新排队，在原机器按已记录分支、精确提交和可还原产物恢复，即使远端分支已前进。远端暂时缺少原提交且工作树尚未改动时，恢复对应引用后可重试并继续同一租约。只有原机器还保存未交付的本地修改。
- 预热模式在创建、轮次结束、切换、取消、删除、回收和重新领取时的整目录快照次数均为零。运行数据只保留 Git 恢复引用、已有产物和队列与租约记录。

## 现场 Unity 验收

选择相同仓库、分支、Editor 版本、镜像与测试命令，固定容器内 `/workspace` 下的仓库相对目录及 Unity `-projectPath`。依次记录普通首次检出、预热槽位首次领取、归还后再次领取的各阶段耗时，并单独记录从启动 Unity 到首个测试开始的时间。检查归还前后目录及 `Library` 标记文件的 inode 和内容，核对整目录快照操作次数为零。用两个槽位同时发起三份混合 SOP/对话请求，分别验证取消和归还后继续，再推进远端分支核对全新检出与精确提交恢复。

本次开发主机没有真实 Unity 项目与 Editor，未取得上述现场时长或导入缓存命中数据。
